# Atlas v0.2 架构

## 产品边界

Atlas 是 Electron 桌面交易工作台。大模型是“提出分析与交易意图的非确定性组件”，不是直接持有账户控制权的执行器。任何订单都必须经过确定性的本地校验与执行链路；生产订单还需要用户二次确认。

```text
Binance 行情 ─> 行情中心 ─> Renderer 展示 ─> AI 上下文
                                  │             │
用户 / Agent ─> 结构化订单意图 ─> 本地校验 ─> 订单执行器 ─> Binance REST
                                  │
                                  └──────────> 操作与审计界面
```

Atlas 不提供提币能力。真实订单没有在开发测试中执行，不能将当前版本视为已经过生产资金验证的自动交易系统。

## 进程与信任边界

- **Renderer / React**：工作台展示和用户交互，不直接访问文件系统、系统凭证或交易所 Secret。
- **Preload**：通过白名单 IPC 暴露行情、账户、订单、AI、MCP、网络测试和凭证状态接口。
- **Electron Main**：管理窗口、系统加密凭证、Binance 签名请求、行情 WebSocket、模型调用、MCP 会话和网络代理。
- **Worker**：当前未拆分。策略调度、回测、持久化订单状态机和更大规模行情归一化仍需在后续版本迁移到独立 Worker。

窗口启用 `contextIsolation`、禁用 Node.js 集成并开启沙箱。外部链接由主进程交给系统浏览器，Renderer 不获得任意进程或文件能力。

## 环境与市场

统一交易接口接受两个正交维度：

| 维度 | 当前选项 | 行为 |
| --- | --- | --- |
| 环境 | Paper | 本地模拟余额和订单，不向 Binance 发送私有下单请求 |
| 环境 | Testnet | 使用 Binance 现货测试网或合约测试网签名 REST |
| 环境 | Live | 使用 Binance 生产 REST；提交订单前要求二次确认标记 |
| 市场 | Spot | Binance 现货账户、订单与公共行情 |
| 市场 | Futures | Binance USDT 永续账户、持仓、订单与公共行情 |

凭证会记录所属环境，选择的环境与凭证不一致时拒绝签名请求。生产环境不自动复用测试网凭证。

## 行情链路

`MarketDataHub` 位于 Electron 主进程，维护现货与 USDT 永续各一条共享 WebSocket：

1. Renderer 按 `marketType + symbol + interval` 订阅主题。
2. 行情中心为 `ticker`、`kline`、`bookTicker` 流维护引用计数。
3. 首个消费者触发 Binance `SUBSCRIBE`，最后一个消费者离开时触发 `UNSUBSCRIBE`。
4. 主进程只向订阅相关主题的窗口广播更新。
5. 连接中断后自动重连，并恢复仍有引用的流。

历史 K 线通过 REST 分页获取，支持 `1m / 5m / 15m / 1h / 4h / 1d`；工作台默认加载 2,000 根，行情服务单次逻辑请求上限为 5,000 根，并使用 15 秒短缓存。实时 K 线在历史数据之上更新当前柱。切换现货/合约、交易对或周期时，Renderer 会取消旧主题并订阅新主题，同时丢弃晚到的旧请求结果。

## 账户与订单

Binance 适配器覆盖：

- 持久化 Paper 余额、持仓、订单、成本与合约配置
- 现货账户、历史订单以及市价/限价订单
- USDT 永续账户、非零持仓、历史订单以及市价/限价订单
- 持仓表逐仓位平仓：现货卖出，单向合约使用反向 `BOTH + reduceOnly`，双向合约使用反向 `LONG / SHORT` 且不发送 `reduceOnly`
- 现货平仓区分总持仓、可用和锁定数量；非 Paper 订单在主进程按 `LOT_SIZE / MARKET_LOT_SIZE / PRICE_FILTER / MIN_NOTIONAL / NOTIONAL` 规整并校验
- 合约 `ONE_WAY / HEDGE` 持仓模式、`positionSide` 与 `reduceOnly` 语义
- 全仓/逐仓、`1-125x` 杠杆以及逐仓保证金增减
- `/fapi/v3/positionRisk` 标记价、强平价、初始/维持保证金与保证金率
- 账户余额、可用余额、已实现/未实现盈亏和实时收益展示

现货账户接口本身不直接提供统一的实时总资产与当日盈亏，因此当前现货快照中的这些聚合值不能替代专业账本。准确收益需要持久化成交、手续费、资金费率、充值转账和基准时点，再按实时价格重估。

生产订单与生产合约账户参数修改分别使用独立的二次确认标记，否则主进程会在网络请求前拒绝。系统未实现提币端点。

## Agent 运行时

Agent 定义和 append-only 事件日志保存在 Electron 用户数据目录。运行时只对闭合 K 线求值；启动时立即检查最近一根已闭合 K 线，WebSocket 短暂断开时由 30 秒 REST 看门狗补偿。处于运行状态的 Agent 会在 Electron 重启后恢复订阅，暂停状态仍保持暂停。当前策略包括 EMA/SMA 交叉、Donchian、RSI、布林带和 ATR 突破。

每次执行依次记录行情快照、信号、风控、意图、提交、交易所响应、成交结果、持仓对账和完成状态。Paper 与 Testnet 在风控通过后可自动执行；Live 只创建 30 秒有效的待确认意图，确认时重新获取价格并再次执行主进程风控。单向合约使用 `BOTH + reduceOnly`，双向合约按策略方向或已有反向仓派生 `LONG / SHORT`，且不会发送 Binance 禁止的 HEDGE `reduceOnly` 参数。

## AI、Skills 与 MCP

模型适配器支持 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 和 Google Gemini，可连接 CCSwitch、本地模型网关或兼容服务。系统消息包含当前市场/账户上下文、启用的 Skill 和“不能绕过风控或主动提交生产订单”的约束。当前对话请求为非流式响应，多会话与历史消息保存在本机用户数据目录。

Skills 目前是工作台内可启停的能力声明，用于约束和补充 AI 上下文；它们不是获得系统权限的快捷方式。

MCP 客户端当前支持 Streamable HTTP：

- `initialize`
- `tools/list`
- `tools/call`
- JSON 或 `text/event-stream` 响应
- `Mcp-Session-Id` 会话保持

当前只允许 HTTP/HTTPS 地址，不支持 stdio MCP Server。远程 MCP 工具的输入仍应被视为不可信数据，涉及订单的工具结果必须回到本地风控和确认链路。

## 凭证与网络

交易所、模型和网络配置由 Electron `safeStorage` 使用操作系统加密能力保存到应用数据目录，文件权限设为 `0600`。状态查询会过滤名称包含 `key`、`secret`、`token` 或 `password` 的字段，避免 Secret 返回 Renderer。

所有远程 REST、WebSocket、模型和 MCP 调用共用网络出口。代理优先级为：

1. `ATLAS_PROXY_URL`
2. `HTTPS_PROXY`
3. `HTTP_PROXY`
4. 应用内加密保存的网络配置

只接受 HTTP/HTTPS 代理。`localhost`、`127.0.0.1` 和 `::1` 自动绕过代理，方便本地 CCSwitch、模型和 MCP 服务直连。应用内代理保存后会触发行情连接重建。

## 实时性与高并发设计边界

当前单实例桌面架构通过共享连接、动态订阅和主进程扇出降低连接数与重复流量；关闭 WebSocket 压缩可减少行情路径上的额外 CPU 开销。这适用于交互式多市场观察和一般自动化交易，但不等于高频交易基础设施。

现阶段的明确限制包括：

- 行情解析、IPC 分发、签名 REST、AI 和 MCP 仍共享 Electron 主进程事件循环
- 没有事件背压、按主题队列上限或慢消费者隔离
- 没有跨进程/跨实例共享订阅与顺序一致性协议
- 没有完整的持久化订单状态机、成交回补和幂等恢复
- 没有端到端延迟 SLO、压测基线或多节点故障切换

面向更高并发与更低延迟的后续建设应优先拆分行情和订单 Worker，增加有界队列与背压、交易所速率限制、序列号与缺口检测、幂等订单键、持久化事件日志、断线补偿、运行指标和告警。生产交易还需要单独的订单审批与熔断服务，而不是只依赖界面状态。

## 风控要求

当前版本提供订单字段校验、环境隔离、生产二次确认和全局风险界面，但完整的自动交易风控仍是建设项。正式接入资金前至少需要：

- 单笔最大名义价值、仓位和杠杆限制
- 账户与策略日内最大亏损/回撤
- 组合净敞口、相关性和集中度限制
- 最小风险回报比、止损必填和价格偏离保护
- 滑点、流动性、订单频率与 Binance 限流控制
- 可恢复的全局紧急停止和撤单流程
- 决策、确认、请求、响应和成交的不可篡改审计

建议始终先使用 Paper，再使用 Testnet，最后才在专用子账户、IP 白名单和最小权限 API Key 下小额验证 Live。
